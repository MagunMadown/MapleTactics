# 월드 랭킹 운영 가이드

이 문서는 기획·개발·운영 담당자가 런 월드 랭킹의 공개 범위와 운영 조건을 확인하기 위한 안내입니다. 현재는 `NORMAL`(일반) 난이도, `balance_2026_10_06` 밸런스, `all_time` 시즌, `ACCOUNT_APPLIED`(계정 성장 보너스 적용), `prototype_run` 노드 그래프, `completion_turns_hits_v1` 정책을 비교합니다. 계정 성장 능력치를 같게 정규화한 도전 모드는 아닙니다.

## 1. 플레이어가 기록을 공개하는 방법

로비의 플레이 기록 NPC/메뉴에서 기존 기록 창을 열고 **내 기록** 또는 **월드 랭킹**을 선택합니다. 내 기록에서 완주한 기록을 선택하면 공개 등록을 진행할 수 있습니다. 이때 공개 등록은 자동이 아닙니다. 안내를 읽고 동의해야 하며, 안내는 8초 동안 표시됩니다. 공개 동의를 하지 않으면 개인 기록으로만 남습니다.

공개 대상은 서버가 확인한 본인 계정의 보존 레코드뿐입니다. Maker, Prototype, Legacy, 미완주 기록, 현재 랭킹 조건과 다른 기록은 공개 목록에서 제외됩니다. 첫 공개 랭킹 버전을 도입할 때 기존 개인 기록을 소급 공개하지 않습니다.

### 기록 창 구성

왼쪽은 5행씩 재사용하는 표이며 월드 랭킹에서는 `순위 / 닉네임 / 직업 / 턴 / 피격 / 클리어`를 표시합니다. 내 기록에서는 앞의 두 열이 `번호 / 종료 결과·날짜`로 바뀝니다. 개인 기록의 번호는 목록 순서이지 랭킹 등수나 RunId가 아닙니다. 이전 기록에 실제 전투 클리어 수가 없으면 해당 열은 `—`로 표시합니다.

오른쪽은 선택한 판의 클리어 수·소비 턴·피격 횟수·시간과 지역 진행·스킬·증강·유물 탭입니다. 선택된 행과 탭은 청록색으로 강조합니다. 검색·즐겨찾기·리플레이 재생·DPS는 이번 화면에 포함하지 않았습니다. 배치 변경은 `UIBuilder`, 표시값은 `RunHistoryUIComponent.RenderTableRow/RenderStatistics/RenderBuild`에서 수정합니다. Screen UI의 배경 순서는 `PreparePanelLayers`에서 처리하며, World UI용 `OrderInLayer`로 대체하지 않습니다. 목록 선택과 탭 전환은 캐시만 읽고 추가 저장소 요청을 하지 않습니다.

## 2. 무엇을 순위로 비교하나요?

계정당 월드 랭킹에는 최고 기록 하나만 반영됩니다. 완료 턴 수가 적을수록 우선이고, 턴 수가 같으면 피격 수가 적은 기록이 우선입니다. 동점은 같은 등수로 표시하며 다음 등수는 건너뜁니다(예: 1, 1, 3). 시간 표시는 참고 정보이며 현재 비교 정책의 순위를 바꾸지 않습니다.

랭킹은 `RunRankingPolicyLogic`의 소비 턴·피격 정책을 따르고, 공개 가능한 결과 필드는 `RunPublicRecordContractLogic`의 허용 목록을 따릅니다. 비공개 시드, HP, 진단 정보는 공개 payload에 포함하지 않습니다. 식별자는 `ProfileCode:RunId` 형식의 불변 `EntryId`입니다. 서로 다른 계정에 같은 RunId가 있어도 충돌하지 않습니다. 지원 범위는 소비 턴 0~100,000, 피격 0~9,999이며 초과 값은 점수를 잘라내지 않고 거절합니다.

## 3. 저장과 개인정보 경계

개인 기록 저장소와 월드 공개 저장소는 분리되어 있습니다. 공개 등록은 `RunRankingServiceLogic`가 본인 기록을 확인한 뒤 `RunRankingRepositoryLogic`를 통해 전용 공개 랭킹 저장소에 기록합니다. 다른 계정의 `UserDataStorage`를 읽지 않습니다.

공개 저장소에는 이름·성적·지역 경로·스킬·증강·유물의 허용된 사본과 ProfileCode 식별자만 저장합니다. 공개 payload(최대 4,000바이트)를 **항상 먼저** 저장하고, 그 다음 SortableDataStorage에 점수와 프로필 태그를 저장합니다. 새 최고 기록으로 교체할 때 알려진 더 낮은 점수의 인덱스만 정리합니다. 동시에 들어온 더 좋은 별도 키는 삭제하지 않습니다. 이미 진행 중인 읽기가 안전하도록 이전 payload는 즉시 지우지 않습니다. 이전 payload의 장기 정리는 향후 GC 운영 항목입니다. **따라서 공개 저장소의 물리 payload 개수가 계정당 항상 1개라는 보장은 없으며, 최고 갱신 횟수만큼 누적될 수 있습니다.**

개인 최근 기록은 기본 10판이며, 목록 밖 개인 최고 원본도 별도로 보존합니다. 이 정책은 공개 랭킹과 독립적이므로 최근 목록 정리 때문에 공개된 최고 빌드가 사라지지 않습니다. 기존 키·보상·유니온 데이터도 변경하지 않습니다.

## 4. 현재 범위와 운영상 한계

- 목록은 상위 20개까지 요청합니다.
- 인덱스 스캔은 최대 1,000개 항목으로 제한됩니다. 저장소가 이 한도를 넘으면 응답이 부분 목록일 수 있습니다.
- 서버 인스턴스의 공용 상위 목록 캐시는 30초이며, 계정별 조회/등록 요청은 각각 10초 간격 제한이 있습니다. 클라이언트의 화면 폴링은 메모리만 읽습니다. 저장소 오류는 5초, 크레딧 소진은 60초 동안 새 상위 조회를 쉬어 요청 폭증을 줄입니다.
- 상위 목록 밖 기록의 정확한 전체 순위는 제공하지 않습니다. 본인 최고 기록이 상위 20개에 없더라도 전체 순위를 계산해 보여주지 않습니다.
- 저장 요청 실패 시 기존 캐시를 유지하고 사용자가 다시 시도해야 합니다. 자동 재등록 FIFO 대기열은 없습니다.
- 동시 요청 중 기존 payload를 유지할 수 있으므로 이전 공개 payload가 바로 삭제된다고 가정하지 마세요.

## 5. 설정 변경과 새 랭킹 보드

랭킹 설정은 별도 CSV가 아니라 Logic 프로퍼티에서 관리합니다. 기본 보드 ID는 `completion_normal_20261006`입니다. 결과 계약의 `BalanceVersion`과 순위 정책의 `BalanceVersion`은 같아야 합니다. **BoardId는 밸런스 문자열과 같은 값이 아니라 독립된 저장소 구분 ID**입니다.

밸런스 변경 시 `RunResultContractLogic.BalanceVersion`과 `RunRankingPolicyLogic.BalanceVersion`을 같은 새 버전으로 바꾸고, `RunRankingPolicyLogic.BoardId`도 **새 ID**로 바꿔 별도 저장 공간을 사용하세요. 시즌·규칙·계정 성장 구분을 바꾸면 결과 계약의 캡처 값과 랭킹 정책을 함께 갱신합니다. 난이도는 실제 첫 전투에서 캡처됩니다. 기존 공개 기록을 새 조건으로 재해석하거나 기존 개인 기록의 조건을 소급 수정하지 않습니다.

`RunRankingPolicyLogic.TopLimit`은 20(1~100 지원), `RunRankingServiceLogic.CacheSeconds`는 30, `RequestInterval`은 10, `RunRankingRepositoryLogic.ScanLimit`은 1,000입니다. 저장소 이름은 Repository의 접두어와 BoardId를 합친 `RunRankingIndexV1:<BoardId>` / `RunRankingPublicV1:<BoardId>`입니다. **전체 저장소 이름은 64바이트 이하여야 합니다.** 정책은 기본 접두어를 고려해 BoardId를 40바이트 이하로 제한합니다. 운영 중 접두어를 바꾸면 기존 데이터가 없어 보이므로 데이터 이관 없이 변경하지 마세요.

## 6. 개발 API 예시

아래 호출은 클라이언트 UI에서 사용하는 요청 형태입니다. 공개 등록 호출은 사용자가 해당 기록을 공개하기로 동의한 뒤에만 실행하세요. 서버는 클라이언트가 보낸 임의 결과를 그대로 신뢰하지 않고, 본인 계정의 보존 기록과 계약 조건을 확인합니다.

```lua
-- 월드 랭킹 요청
_RunRankingServiceLogic:RequestWorldRanking()

-- 로컬 캐시의 월드 랭킹 스냅샷 조회
local snapshot = _RunRankingServiceLogic:GetLocalWorldRankingSnapshot()
-- Success, Reason, IsLoaded, Revision, Entries, OwnBest, OwnBestReason, ScanLimited
-- Entries[i]: EntryId, Nickname, Rank, Record(성적/Build/RegionHistory)

-- 선택한 완주 기록의 공개 동의를 받은 뒤 등록 요청
_RunRankingServiceLogic:RequestPublishMyRun(runId, true)
```

내 기록 화면은 `RunHistoryUIComponent`에서 개인 기록과 공개 등록 동의를 연결합니다. 결과 필드나 정렬 방식을 바꾸려면 `RunResultContractLogic`, `RunPublicRecordContractLogic`, `RunRankingPolicyLogic` 및 저장소·서비스 구현을 함께 확인하고, 계약과 표시 설명도 일치시키세요.

## 7. 확인된 검증과 미검증 범위

2026-10-06 Maker의 네이티브 격리 저장소에서 공개 기록 4회 등록, 새 최고 기록 반영, 중복 등록 무시, 본인 최고 기록 태그, 세 계정 순위 `1, 2, 2`, 빌드 유지가 통과했습니다. 테스트 인덱스와 payload 키 각 4개를 정리한 작업도 종료 코드 0으로 완료됐습니다. 기존 개인 기록 15개와 공개 기록 13개, 총 28개 로컬 Lua mock 회귀도 통과했습니다. Maker에서 대상 클라이언트 전송·DTO 복원·공개 행/스킬 탭/내 공개 최고/두 화면 전환·2회 공개 동의의 버튼 이벤트 경로를 확인했습니다. 클라이언트 화면에 임의 RunId를 넣어 등록을 시도해도 서버 보존 기록에 없으면 거절됨을 확인했습니다. fixture는 화면 메모리에만 넣었고 실제 사용자 저장에는 합성 기록을 쓰지 않았습니다.

최종 소스로 격리 저장소 등록·조회·그래프/결과 규칙 메타데이터 보존을 다시 검사하고 정확한 테스트 키를 삭제했습니다. 실제 Escape 키 입력으로 창 닫기와 동의 상태 초기화를 확인했습니다. 마지막 Play 재시작의 대상 RPC·월드 목록 조회는 `RANKING_LOADED`, build/runtime Error·Warning 0이었습니다. Maker는 검사 후 편집 모드로 돌려두었습니다.

여러 실제 인스턴스 간 동작, 출시 환경의 실제 전체 완주, 모바일 및 물리 포인터 조작은 미검증입니다. 동시 등록/부분 실패/조회 상한은 로컬 mock으로 검사했으며 실제 네트워크 장애를 강제로 재현한 시험은 아닙니다. Maker 기본 버튼의 mouse_input 제약 때문에 버튼 이벤트 경로를 검사했으며 이를 실제 클릭 검증으로 간주하지 않습니다. 공식 기본/고급 랭킹 패키지는 조사했지만 기존 저장·UI 경계를 보존하기 위해 통째로 설치하지 않았습니다.

### 표·상세 패널 UI 변경 회귀 (2026-10-06)

Luna 에이전트가 UIBuilder 배치 작업을 맡고, 메인에서 표 데이터 연결·선택 색상·Screen UI 형제 순서를 검토했습니다. 기존 UUID/경로와 저장·등록 규격은 유지했습니다. 통계 숫자 영역은 글자 높이에 여유를 두도록 확장했고 배경이 글자 위에 덮이지 않도록 초기 표시 순서를 처리했습니다.

로컬 mock 29개가 통과했습니다. Maker에서는 실제 개인 기록 조회, 메모리 전용 공개 샘플 5행, `1·2·2·4·5` 공동 순위 표시, 행 선택에 따른 통계 변경, 4종 상세 탭, 지역 상세 2페이지, 공개 목록 2페이지 및 남는 행 숨김을 검사했습니다. 버튼 연결은 `ButtonClickEvent`로 검사했고 Esc는 실제 키 입력으로 확인했습니다. 샘플은 실제 저장소에 쓰지 않았습니다. 최종 Play 재시작 후 표시 순서와 값 연결을 다시 확인했고 build/runtime Error·Warning은 0이었습니다. PC 화면은 확인했으며 모바일 및 실제 마우스 hit 영역 검증은 여전히 별도입니다.
