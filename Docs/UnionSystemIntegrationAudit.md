# Union System Integration Audit

## Scope and baseline

- Audit date: 2026-08-28 (Asia/Seoul)
- Audit target: the current worktree on `codex/cooldown-utility-hud` at `4dda4ab`, including current uncommitted workspace files.
- This is Step 0 only. No production `.mlua`, `.ui`, `.csv`, `.userdataset`, `.model`, `.map`, or gameplay data was changed.
- Lobby map inspection used `MapBuilder`. `map/lobby.map` is `TileMapMode = 0` (MapleTile), gravity `1`, non-instance, with `script.LobbyGridMovementComponent` on the map root.
- UI inspection used `UIBuilder`; raw `.ui` JSON was not edited.

## Executive findings

1. There is no player-persistent save/load or player profile implementation. No `_DataStorageService`, `GetUserDataStorage`, `GetGlobalDataStorage`, `GetAsync`, `SetAsync`, `GetAndWait`, or `SetAndWait` call exists under `RootDesk/MyDesk`.
2. Current progression is player-entity, run-scoped state held by `PlayerRunStateComponent`, `PlayerRunInventoryComponent`, and `PlayerRunAugmentComponent`. It is synchronized in-session but not persisted across sessions.
3. The current run currency is `gold`, not meso. `CurrencyDefinitions.csv` explicitly classifies it as `RUN_SCOPED`.
4. The augment system currently grants a job passive as one unique augment. There is no augment offer/choice pool, reroll counter, or reroll API.
5. No relic/artifact ownership system and no random relic grant path exist. The only `Relic` occurrence is a comment describing a generic queue-capacity modifier entry point.
6. Starting potion count is currently zero: `PlayerRunInventoryComponent:ResetForRun()` clears consumables and no start-of-run potion grant follows.
7. Result presentation is asymmetric: a defeat panel exists in `BattleQueueHUD`; victory records rewards and transitions to a reward map after 1.5 seconds without a full victory/result summary screen.

## Recommended integration boundaries for the next design step

1. **Permanent account boundary:** new server-only Union profile service using `UserDataStorage`, schema versioning, idempotent mutations, and a client-safe snapshot/revision.
2. **Lobby presentation boundary:** separate Union UIGroup and client Logic following the existing CharacterSelection/Collection path-resolution pattern.
3. **Run modifier boundary:** one immutable Union bonus snapshot applied only for `NEW_RUN`, before HP/inventory/starting-skill finalization.
4. **Reward boundary:** authoritative `RunManagerLogic:RecordBattleResult()` success path with a permanent reward receipt keyed from the existing battle record key.
5. **Content boundary:** do not overload `JobDefinitions`, `PlayerRunInventoryComponent`, or `PlayerRunAugmentComponent` with permanent ownership. Reference stable job IDs but keep Union data in its own versioned dataset/profile model.
